# v0.1.0 キー設計（採用案）

**次の一手:** この表どおりに DynamoDB へ品目を Put し、Streams → 判定 Lambda を通す。

## アクセスパターン（埋めた表）

| 操作 | 必要な検索 | 採用キー |
| --- | --- | --- |
| 品目の在庫・しきい値の取得 / 更新 | 品目 ID で1件 | `pk=ITEM#<itemId>`, `sk=META` |
| Streams 変更が品目の在庫更新か判定 | レコード種別またはキー形状 | `sk=META` かつ `entityType=ITEM` |
| 補充リクエスト新規作成 | 品目 ID + 起動の一意性 | `pk=ITEM#<itemId>`, `sk=RESTOCK#<streamEventId>` |
| 同一イベント再処理で重複しない | 条件付き書き込み用の一意キー | 上記 `sk` に Stream `eventID` を使う |

## 採用: 単一テーブル（アイテムと補充をキー形状で分ける）

- テーブル名（論理）: `HouseholdRestock`
- 品目: `pk=ITEM#toilet-paper`, `sk=META`, 属性 `entityType=ITEM`, `stock`, `threshold`
- 補充リクエスト: `pk=ITEM#toilet-paper`, `sk=RESTOCK#<eventID>`, 属性 `entityType=RESTOCK`, `itemId`, `stock`, `threshold`, `streamEventId`

理由: v0.1 の読み書きは品目 ID 起点だけで足りる。単一テーブルなら SAM のリソースが1つで、Streams のフィルタもキー／属性で切れる。後からテーブル分割へ移すのも、キー接頭辞が残っていれば可逆。

## 不採用案と理由

| 案 | 不採用の理由 |
| --- | --- |
| 品目テーブルと補充テーブルの2本 | v0.1 では結合も GSI も不要。IAM・Streams・削除手順が増えるだけ |
| `pk=itemId` のみ（sk なし） | 補充行を同キーに載せられず、再帰防止と冪等キーが別設計になる |
| 補充の sk を時刻や実行 ARN だけにする | 同一 Stream イベントの再処理と1対1にならない |

## 再帰起動の防ぎ方（採用）

**Streams のイベントソースマッピングで `entityType=ITEM`（かつ `sk=META`）にフィルタ**し、補充行の書き込みは Lambda に届かないようにする。  
理由: 記録用 Put が判定を再起動する経路を、インフラ側で切るのが最短。Lambda 内でも同じ条件を再確認する（防御の二重化）。

## 同一イベント冪等（採用）

1. Step Functions の実行名を `restock-<itemId>-<eventID>`（許可文字に整形）にし、同じイベントでは `ExecutionAlreadyExists` になる  
2. 補充 PutItem は `attribute_not_exists(pk) AND attribute_not_exists(sk)`。`sk` に `eventID` を含むので再 Put は条件失敗 → 成功扱い

理由: 「起動」と「記録」の両方で同一 `eventID` を鍵にし、要件8（別更新でも2本目なし）とは独立に、同一イベント再処理だけを止める。
