## 学習のゴール

架空の日用品データで **Lambda・Step Functions・DynamoDB** を学ぶ。  
最小画面から在庫更新・承認・状態確認ができるところまでを、小さい検証可能な単位で進める。

時間は**推定**（実績ではない）。環境整備に使った時間は含めない。  
版合計 **約 30〜43 時間** + AWS 権限・保護・不具合修正の余裕 **約 5〜7 時間** ≒ **約 35〜50 時間**（週 8〜10 時間ならおおよそ 4〜6 週）。厳密な期日約束ではない。元要件の「30〜40 時間」は環境込みの目安だったので、**ここでは確約しない**。

## 全体の完了条件

1. しきい値**以下**でちょうど 1 本起動し、さらに減らしても 2 本目なし
2. 承認放置は timeout 却下、在庫は変わらない
3. 一時注文失敗は Retry で回復。継続失敗は取消経路を実行履歴で確認できる
4. 到着通知 2 回でも在庫加算は 1 回
5. 配送待ちが指定日時に自動再開する（検証は待ちを短くしてよい）
6. スタック削除 → 再デプロイで同じ動きが再現できる
7. 最小画面から在庫更新・承認/却下・状態確認ができる（v0.3.0 以降）

## 全体でやらないこと

- 本物の通販・決済
- 凝った見た目・複雑な装飾
- VPC / RDS / 本番アプリ用コンテナ
- 本格ログイン基盤
- 在庫履歴・CQRS（現在在庫だけ）
- 発展要件を完成の必須にすること

**画面について:** 元ページは「見た目にこだわった画面は不要（承認は URL でよい）」だった。最新方針では**最小画面を完成に含める**。  
v0.1.0 の「画面なし」は**その版の非範囲**であり、全体方針の否定ではない。

## 検証の共通ルール

| 層 | できること | できないこと / 注意 |
| --- | --- | --- |
| いま（環境+品質ツール） | `./scripts/check.sh`（unit/coverage/ruff/vulture/ty/e2e doctor）。coverage は骨格のみで**業務品質を示さない**。e2e シナリオは未作成 | 業務・画面の正しさは保証しない。`e2e run` はシナリオ0件で公式どおり失敗 |
| ローカル（各版実装後） | 純ロジック、API 境界、状態遷移、模擬再送、画面操作（e2e は v0.3.0 以降）、`sam validate`/`build`（template がある版） | Streams / IAM / SFN の本番時間挙動を SAM Local だけで保証しない |
| AWS（ユーザー側） | 実起動数、並行、timeout、callback、Retry/Catch、Wait、直接更新、補償履歴、画面 API、削除再作成 | エージェントは AWS 接続・デプロイ・削除を**しない**。計画上はユーザー実施 |

実装済みでも AWS 未検証なら **「実装済み・AWS 検証待ち」** とし、完成扱いにしない。
