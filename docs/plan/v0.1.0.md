## 実装する流れ（将来）

架空の**1品目**だけ。

1. DynamoDB に現在在庫としきい値を保存する
2. 手動で在庫を更新する（コンソール / CLI / 小さなスクリプト。画面は作らない）
3. DynamoDB Streams の変更で判定 Lambda が動く
4. 補充対象なら Standard Step Functions を起動する（品目 ID を渡す）
5. ワークフローは補充リクエストを DynamoDB に1件書いて終了する
6. 上記を SAM で定義する

承認・注文・配送待ち・在庫加算は行わない。

## 判定条件

- **採用:** 在庫数 **≦ しきい値**（以下）
- 原文は「しきい値を**下回ったら**」（`<`）だが、MVP 全体の完了条件は「しきい値**以下**でちょうど1本起動…」
- **全体完了条件を優先**し、v0.1.0 は「以下（≦）」。原文との差は意図的

## データとキー

キーはアクセスパターンを先に洗い出してから決める（実装時に確定）。

| 操作 | 必要な検索 |
| --- | --- |
| 品目の在庫・しきい値の取得 / 更新 | 品目 ID で1件 |
| Streams 変更が品目の在庫更新か判定 | レコード種別またはキー形状 |
| 補充リクエスト新規作成 | 品目 ID + 起動の一意性に使える値 |
| 同一イベント再処理で重複しない | 条件付き書き込み用の一意キー / 属性 |

単一テーブルか複数かは、上を満たす可逆な最小構成を実装時に選ぶ。  
在庫履歴や CQRS は扱わない（現在の在庫数だけ）。

## 処理の境界

```
[手動在庫更新]
      ↓
[DynamoDB: 品目（在庫・しきい値）]
      ↓ Streams
[判定 Lambda]
      ├─ 対象外 → 終了（起動しない）
      └─ 対象   → Standard Step Functions（品目 ID）
                      ↓
                [補充リクエストを DynamoDB に記録して終了]
```

## 受け入れ条件（実装時。いまは未達成でよい）

1. **対象外なら起動しない**  
   在庫がしきい値より大きい更新、品目以外の変更、必要属性欠けなど
2. **対象なら品目 ID 付きの補充リクエストを残す**
3. **補充リクエスト記録で再帰起動しない**  
   判定除外や別テーブルなどで防ぐ
4. **同一イベント再処理で補充リクエストを重複作成しない**  
   条件付き書き込みなど

### 後続（このバージョンでは保証しない）

- **別イベントの連続更新に対する、品目単位の実行中1本制御**  
  MVP 全体完了条件（しきい値以下のあと、さらに減らしても2本目なし）は後続  
  受け入れ条件 4（同一イベント再処理の冪等）と**混同しない**

## やらないこと

- 承認待ち / タイムアウト却下
- 模擬注文、Retry / Catch、Wait
- 配送後の在庫加算、サーガ補償
- durable functions 比較
- 画面・本格認証・VPC / RDS / コンテナ（本番アプリ基盤）
- 本物の通販・決済、在庫履歴・CQRS
- **いまの作業での機能実装そのもの**（計画と環境のみ）

### 将来の検証案（実装後・AWS デプロイ後）

1. しきい値より多い在庫 → 起動しない
2. しきい値以下 → ワークフロー1本、補充リクエスト1件
3. 補充リクエスト側の書き込みだけでは追加起動しない
4. 同じイベント再投入でも補充リクエストが増えない

`sam local` やモックでは Streams・IAM・実タイミングまで完全再現できない。結合の合格は AWS 上の確認を正とする。
