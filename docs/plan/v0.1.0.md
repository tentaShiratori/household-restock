## 目的（学習）

日用品の自動補充プロジェクトの1週目として、要件 1・2・9 に相当する次を、小さい縦割りで体験できるようにする。

| 要件 | このバージョンで触るところ |
| --- | --- |
| 1. 品目と補充リクエストを DynamoDB に置く | テーブル設計（アクセスパターン起点のキー） |
| 2. 在庫がしきい値条件を満たしたらワークフロー起動 | DynamoDB Streams → 判定 Lambda → Step Functions |
| 9. すべてを IaC で定義し消して作り直せる | AWS SAM（`template.yaml` 等） |

## スコープ（将来このバージョンで実装するもの）

架空の**1品目**について、次の流れだけを実装する。

1. DynamoDB に「現在在庫」と「しきい値」を保存する
2. 手動で在庫を更新する（AWS コンソール / CLI / 小さなスクリプト想定。画面は作らない）
3. DynamoDB Streams の変更イベントをきっかけに判定 Lambda が動く
4. 判定が「補充対象」なら、Standard の Step Functions を起動する
5. ワークフローは DynamoDB に**補充リクエストを1件記録して終了**する
6. 上記リソースを SAM で定義する

この時点では承認・注文・配送待ち・在庫加算は行わない。

### 判定条件（しきい値との比較）

- **採用する条件**: 在庫数 **≦ しきい値**（「以下」）
- 原文の要件文言は「しきい値を**下回ったら**」（厳密には `<`）だが、MVP 全体の完了条件は「在庫をしきい値**以下**にするとワークフローがちょうど1本起動し…」である
- **全体完了条件を優先**し、v0.1.0 では「以下（≦）」を採用する。原文との差は意図的である

### データとキー設計の方針

キーは先にアクセスパターンを洗い出してから決める（実装時に確定）。

想定する読み書き（たたき台。実装前に見直してよい）:

| 操作 | 必要な検索 |
| --- | --- |
| 品目の現在在庫・しきい値を取得 / 更新 | 品目 ID で1件取得・更新 |
| Streams から来た変更が「品目の在庫更新」か判定 | レコード種別またはキー形状で区別 |
| 補充リクエストを新規作成 | 品目 ID + 起動の一意性に使える値が必要 |
| 同一イベントの再処理で重複作成しない | 条件付き書き込み用の一意キー / 属性 |

単一テーブルか複数テーブルかは、上記パターンを満たす**可逆な最小構成**を実装時に選ぶ。  
在庫の履歴や CQRS は扱わない（現在の在庫数だけ持つ）。

### 処理の境界

```
[手動在庫更新]
      ↓
[DynamoDB: 品目（在庫・しきい値）]
      ↓ Streams
[判定 Lambda]
      ├─ 対象外 → 何もしないで終了
      └─ 対象   → Standard Step Functions 起動（品目 ID を渡す）
                      ↓
                [補充リクエストを DynamoDB に記録して終了]
```

## 受け入れ条件（実装時。いまは未達成でよい）

1. **対象外なら起動しない**  
   在庫がしきい値より大きい更新、品目以外のレコード変更、判定に必要な属性が欠けるイベントなどでは Step Functions を起動しない。
2. **対象なら品目 ID を引き継いだ補充リクエストを記録する**  
   起動されたワークフローが、渡された品目 ID 付きの補充リクエストを DynamoDB に残して終わる。
3. **補充リクエスト記録による再帰起動をしない**  
   補充リクエスト用レコードの書き込みが Streams 経由で再び「補充開始」にならない（判定で除外する、別テーブルにする、など）。
4. **同一イベントの再処理でも補充リクエストを重複作成しない**  
   少なくとも「同じ起動イベントを再度処理した場合」は、条件付き書き込み等で同じ補充リクエストを二重に作らない。

### このバージョンでは保証しないこと（後続）

- **別イベントの連続更新に対する、品目単位の「実行中は1本」制御**  
  MVP 全体完了条件（しきい値以下にしたあと、さらに減らしても2本目が起動しない）は、実行中フラグや一意な実行名など後続バージョンの課題である。  
  v0.1.0 の受け入れ条件 4（同一イベント再処理の冪等）と**混同しない**。

### 将来の検証案（実装後・AWS デプロイ後）

1. しきい値より多い在庫に更新 → ワークフローが起動しない
2. 在庫をしきい値以下に更新 → ワークフローが1本起動し、補充リクエストが1件残る
3. 補充リクエスト側の書き込みだけでは追加のワークフローが起動しない
4. 判定 Lambda に同じイベントを再投入しても補充リクエストが増えない

ローカルの `sam local` やモックでは、Streams 連携や IAM・実サービス間のタイミングまで**完全には再現できない**。結合の合格は AWS 上の確認を正とする。
